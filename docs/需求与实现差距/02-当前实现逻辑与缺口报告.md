# 毕业设计管理系统当前实现逻辑与缺口报告

> 本报告由主流程审阅和 subagent 只读审阅结果整理而成，基于当前仓库 `D:\Myproject\jspproject\毕业设计管理系统`。重点分析核心业务模块：角色边界、教师出题、专业负责人审题、学生选题、专业负责人确认/强制分配、资料上传、成绩/答辩。AI 助手、公告、消息、模板、统计图表等非核心模块不展开。

---

## 1. 当前系统主流程概览

当前系统已经能跑通一条简化版毕业设计流程：

```text
管理员维护用户/专业数据
  -> 教师提交题目
  -> 专业负责人审核题目
  -> 学生申请一个题目
  -> 教师填写建议意见
  -> 专业负责人最终确认或退回
  -> 专业负责人可手动分配未选题学生
  -> 学生上传开题/中期/终稿资料
  -> 教师审核资料、填写分数和评语
  -> 管理员安排答辩，学生查看成绩
```

但它目前还不是老师要求的完整“三志愿 + 两轮选题 + 一题一人”模型。最主要差距集中在选题模块。

## 2. 基础用户与角色边界

### 2.1 当前数据流

| 功能 | URL / JSP | Controller / Filter | DAO | 数据表 | 返回 |
|---|---|---|---|---|---|
| 登录 | `WebContent/login.jsp` -> `/login.action` | `src/controller/LoginController.java` | `UserDao` | `users` | 成功进入 `/dashboard.action` |
| 鉴权 | 所有非公开路径 | `src/filter/AuthFilter.java` | `UserDao`、`MessageDao` | `users`、`messages` | 无权限跳 dashboard 或 login |
| 用户管理 | `/admin/user.action`、`WebContent/admin/users.jsp` | `AdminUserController` | `UserDao` | `users` | 用户管理页 |

| 系统开关 | `/admin/system-switch.action` | `AdminSystemSwitchController` | `SystemConfigUtil` | `system_configs` | 开关管理页 |

### 2.2 当前实现逻辑

- `AuthFilter` 根据 URL 前缀做权限控制：
  - `/admin/` 只允许 `admin`。
  - `/director/` 只允许 `director`。
  - `/teacher/` 调用 `RoleUtil.hasRole(user, "teacher")`。
  - `/student/` 只允许 `student`。
- `RoleUtil.hasRole()` 中规定：`director` 也可以被视为 `teacher`，所以专业负责人可以访问教师端。
- `ScopeUtil.directorScope(user)` 要求专业负责人账号必须有 `college` 和 `major`，专业负责人页面都依赖这个范围。
- 管理员可以新增、编辑、删除用户，也可以批量导入教师和学生，重置学生密码。

### 2.3 对照需求状态

**状态：部分实现。**

已实现：

- 四类角色已经存在：`admin/director/teacher/student`。
- 管理员有基础用户维护、批量导入、重置密码能力。
- 专业负责人能按 `college + major` 限定数据范围。

主要差距：

- 专业负责人可以进入教师端，这在技术复用上能理解，但角色边界不是完全干净。
- 专业负责人范围完全依赖账号上的 `college/major`，如果基础数据录错，会直接导致专业负责人无法工作。
- 用户删除是物理删除，已有外键关联时可能失败；更稳的业务逻辑应优先禁用用户。

### 3.3 对照需求状态

**状态：部分实现。**

主要差距：

- **题目审核通过后没有严格锁定。**只要教师端出题开关开启，教师仍可编辑自己已经 `open/closed` 的题目，并让它重新变成 `pending`。

- 删除题目没有业务层判断“已审核/已有申请/已有确认时不能删”，主要依赖数据库外键或执行失败兜底。

### 4.2 当前实现逻辑

关键文件：

- `src/controller/DirectorTopicReviewController.java`
- `src/dao/TopicDao.java`
- `WebContent/director/topic-review.jsp`

当前逻辑：

- 专业负责人访问时先通过 `ScopeUtil.directorScope(user)` 取得 `college/major`。

### 4.3 对照需求状态

**状态：主要流程已实现，但锁定不足。**

已实现：

- 专业负责人负责审题。
- 审题范围限制在本专业。
- 学生只能看到审核通过后的 `open` 题目。

主要差距：

- 题目通过后没有进入不可修改的锁定状态。
- `TopicDao.review()` 允许对 `pending/rejected/open/closed` 状态都执行审核更新，不只限定待审核题目。
- 专业负责人也可以继续调整已通过题目的标题、描述和最大人数，缺少“审核通过后稳定”的业务限制。

## 5. 学生选题模块

### 5.1 当前数据流

| 功能 | URL / JSP | Controller | DAO | 表/字段 | 返回 |
|---|---|---|---|---|---|
| 查看可选题目 | `/student/topic.action`、`WebContent/student/topics.jsp` | `StudentTopicController.doGet()` | `TopicDao.findOpenTopics()`、`SelectionDao.hasPendingOrApproved()` | `topics`、`topic_selections` | 学生题目页 |
| 申请题目 | `/student/topic.action?action=apply` | `StudentTopicController.doPost()` | `SelectionDao.apply()` | `topic_selections.student_id/topic_id/status/round/apply_reason` | redirect 我的选题 |
| 查看我的选题 | `/student/my-selection.action`、`WebContent/student/my-selection.jsp` | `StudentSelectionController.doGet()` | `SelectionDao.findByStudent()` | `topic_selections` JOIN `topics/users` | 我的选题页 |

### 5.2 当前实现逻辑

关键文件：

- `src/controller/StudentTopicController.java`
- `src/controller/StudentSelectionController.java`
- `src/dao/SelectionDao.java`
- `src/dao/TopicDao.java`
- `WebContent/student/topics.jsp`
- `WebContent/student/my-selection.jsp`

`StudentTopicController.doGet()` 当前逻辑：

1. 从 session 取当前学生。
2. 读取学生 `college/major`。
3. 检查选题总开关 `switch.selection`。
4. 调用 `TopicDao.findOpenTopics(keyword, college, major)` 查询：
   - `topics.status='open'`
   - `selected_count < max_students`
   - `college/major` 与学生一致。
5. 调用 `SelectionDao.hasPendingOrApproved(studentId)` 判断学生是否已有有效申请。
6. forward 到 `student/topics.jsp`。

`SelectionDao.apply()` 当前逻辑：

1. 开启事务。
2. `SELECT role,status,college,major FROM users WHERE id=? FOR UPDATE` 锁定学生。
3. 检查学生是启用状态学生。
4. 检查 `switch.selection` 是否开启。
5. 检查学生是否已有 `pending` 或 `approved` 记录。
6. `SELECT status,max_students,selected_count,college,major FROM topics WHERE id=? FOR UPDATE` 锁定题目。
7. 检查题目是 `open`、未满额、与学生同学院同专业。
8. 插入一条 `topic_selections` 记录：`status='pending'`，`round=SystemSwitchUtil.currentRound()`。

### 5.3 对照需求状态

**状态：部分实现，但没有实现老师强调的核心三志愿模型。**

已实现：

- 学生只能看到本专业已审核通过的题目。
- 学生不能对其他专业题目提交申请。
- 学生不能同时拥有多个 `pending/approved` 申请。
- 申请记录有 `round` 字段。

主要差距：

1. **三志愿未实现。**
   - 当前页面是每次点一个题目并填写申请理由。
   - `topic_selections` 一条记录只对应一个题目。
   - 没有 `choice_rank`、第一志愿、第二志愿、第三志愿的概念。
   - `hasPendingOrApproved()` 直接限制学生只有一个活跃申请，和“三个志愿”冲突。

2. **每题最多 3 个学生意向未实现。**
   - 当前只检查 `topics.selected_count < topics.max_students`。
   - `selected_count` 表示已确认人数，不是待确认意向人数。
   - 没有统计一个题目当前有多少学生把它填为志愿。
   - 所以同一题目可能收到超过 3 个 `pending` 申请。

3. **最终一题一人没有强制。**
   - `topics.max_students` 可以大于 1。
   - 专业负责人确认时只检查 `selected_count < max_students`。
   - 如果某题 `max_students=3`，系统允许最终确认 3 名学生。

4. **第二轮规则没有完整实现。**
   - 有 `round` 字段和 `selection.current_round` 配置。
   - 但没有完整的“第一轮结束 -> 未匹配学生进入第二轮 -> 未分配题目进入第二轮”的状态机。
   - 当前更多是靠开关和人工状态管理。

## 6. 教师建议、专业负责人确认与强制分配

### 6.1 教师建议数据流

| 功能 | URL / JSP | Controller | DAO | 表/字段 | 返回 |
|---|---|---|---|---|---|
| 查看自己题目下的申请 | `/teacher/selection.action`、`WebContent/teacher/selections.jsp` | `TeacherSelectionController.doGet()` | `SelectionDao.findByTeacher()` | `topic_selections` JOIN `topics` | 教师选题建议页 |
| 填写建议通过/不通过 | `/teacher/selection.action?action=approve/reject` | `TeacherSelectionController.doPost()` | `SelectionDao.review()` | `topic_selections.review_comment/review_time` | redirect 教师选题建议页 |

当前逻辑：

- 教师点击“建议通过/建议不通过”后，并不改变 `topic_selections.status`。
- `SelectionDao.review()` 只是追加 `review_comment` 和 `review_time`。
- 日志动作是 `SUGGEST_APPROVE` 或 `SUGGEST_REJECT`。
- 消息文本也说明最终结果以专业负责人确认为准。

**状态：符合“教师不是最终确认人”的要求。**

### 6.2 专业负责人确认数据流

| 功能 | URL / JSP | Controller | DAO | 表/字段 | 返回 |
|---|---|---|---|---|---|
| 查看本专业申请 | `/director/selection-confirm.action`、`WebContent/director/selection-confirm.jsp` | `DirectorSelectionConfirmController.doGet()` | `SelectionDao.findByDirectorScope()` | `topic_selections`、`topics`、`users` | 选题确认页 |
| 确认/不确认 | `/director/selection-confirm.action?action=confirm/reject` | `DirectorSelectionConfirmController.doPost()` | `SelectionDao.confirmByDirector()` / `rejectByDirector()` | `topic_selections.status/review_comment/review_time`，`topics.selected_count/status` | redirect 确认页 |
| 手动分配 | `/director/selection-confirm.action?action=assign` | `DirectorSelectionConfirmController.doPost()` | `SelectionDao.manualAssign()` | 插入 `topic_selections(status='approved')`，更新 `topics.selected_count/status` | redirect 确认页 |

当前确认逻辑：

- `SelectionDao.reviewInDirectorScope()` 只处理 `pending` 申请。
- 确认时检查：
  - 申请、题目、学生都在专业负责人范围内。
  - 题目状态是 `open`。
  - `selected_count < max_students`。
  - 学生没有其他 `pending/approved` 记录。
- 确认后：
  - 当前申请变成 `approved`。
  - 题目 `selected_count + 1`。
  - 如果满额，则题目变为 `closed`。

当前手动分配逻辑：

- 查询未选题学生使用 `findUnselectedStudents(college, major)`。
- 查询可分配题目使用 `TopicDao.findOpenTopics(null, college, major)`。
- `manualAssign()` 直接插入 `status='approved'` 的 `topic_selections` 记录。

### 6.3 对照需求状态

**状态：确认主线已实现，强制分配部分实现，但缺三志愿和一题一人。**

已实现：

- 最终确认由专业负责人完成。
- 教师只是给建议，不改变最终状态。
- 专业负责人可以手动分配未选题学生。
- 专业负责人确认和分配都有专业范围限制。

主要差距：

- 确认页面无法按第一志愿、第二志愿、第三志愿展示候选人，因为底层没有志愿顺序。
- 没有“按题目聚合候选学生，并显示每人是第几志愿”的核心界面。
- 手动分配的“未选题学生”排除了 `pending` 学生；如果第一轮结束后还有待确认但未 approved 的学生，当前逻辑可能不符合“未最终匹配”的定义。
- 可分配题目只看 `selected_count < max_students`，而不是“题目没有最终分配记录”。当 `max_students > 1` 时不符合“一题一人”。

| 教师审核/退回 | `/teacher/document.action?action=review/reject` | `TeacherDocumentController.doPost()` | `DocumentDao.review()` | `documents.status/score/feedback/self_review/peer_review/review_time/reviewer_id` | redirect 教师资料页 |

### 7.2 当前实现逻辑

关键文件：

- `src/controller/StudentDocumentController.java`
- `src/controller/TeacherDocumentController.java`
- `src/dao/DocumentDao.java`
- `src/dao/DocumentVersionDao.java`

学生上传前置：

- 必须存在 `SelectionDao.findApprovedByStudent()`，也就是已经最终确认题目。
- 文档类型必须存在于字典 `document_type`。
- 上传开关按类型控制：
  - `switch.upload_proposal`
  - `switch.upload_midterm`
  - `switch.upload_final`
- 阶段顺序：
  - `proposal` 无前置。
  - `midterm` 要求 `proposal` 已 `reviewed`。
  - `final` 要求 `midterm` 已 `reviewed`。
- 已提交或已审核文档会锁定，只有被退回 `rejected` 后才能重新提交。
- 重新提交会把旧内容存入 `document_versions`。

教师审核：

- 只有题目的指导教师可以审核对应文档。
- 通过时必须填写 0 到 100 的分数。
- 退回时清空分数、自评、互评。

### 7.3 对照需求状态

**状态：主要流程已实现。**

已实现：

- 已确认题目后才能上传资料。
- 开题、中期、终稿有阶段顺序。
- 教师可以审核通过或退回。
- 被退回后可以重交，并有版本记录。

主要差距：

- 当前文档审核完全由指导教师完成，没有扩展到评阅教师或答辩组。
- 如果要做完整版 40%/20%/40% 成绩，需要增加评阅教师分配和评分。

- 答辩成绩由管理员录入，不是答辩组或教师录入。
- 没有最终总评成绩计算。
- 没有导师自评 40%、评阅教师 20%、答辩 40% 的完整毕业论文成绩模型。
- 没有评阅教师分配模块。

## 9. 当前数据库对核心业务的支撑情况

### 9.1 `users`

当前已支撑：

- 登录账号。
- 四类角色。
- 学院、专业、班级、学号。
- 专业负责人范围。

风险：

- 专业范围写在用户表中，必须保证数据准确。

### 9.2 `topics`

当前字段：

- `teacher_id`
- `college`
- `major`
- `max_students`
- `selected_count`
- `status`
- `review_comment`
- `reviewer_id`
- `review_time`

已支撑：

- 教师出题。
- 专业负责人审题。
- 学生按专业查看开放题目。
- 题目容量控制。

不足：

- `max_students` 让系统天然支持一题多人，不符合老师要求的最终一题一人。
- 没有专门的“题目锁定”字段。
- `selected_count` 是最终确认人数，不是意向人数。

### 9.3 `topic_selections`

当前字段：

- `student_id`
- `topic_id`
- `status`
- `round`
- `apply_reason`
- `review_comment`
- `apply_time`
- `review_time`
- `active_guard`

已支撑：

- 单题申请。
- 申请状态。
- 轮次记录。
- 一个学生只能有一个 `pending/approved` 活跃申请。

不足：

- 不支持三志愿。
- 不支持志愿顺序。
- 不支持同一轮一个学生提交 1 到 3 个志愿。
- 不支持统计某题本轮意向人数上限 3。
- 没有独立最终分配表，申请和最终结果混在一起。

### 9.4 `documents` / `document_versions`

当前支撑较完整：

- 学生按类型提交资料。
- 指导教师审核。
- 阶段顺序控制。
- 退回重交版本记录。

### 9.5 `defense_schedules`

当前支撑：

- 答辩时间、地点、组别、成绩、评语。

不足：

- 没有答辩组教师、多评委评分和总评规则。

## 10. 老师重点需求对照表

| 老师需求 | 当前状态 | 当前证据 | 说明 |
|---|---|---|---|
| 管理员管理基础数据 | 已实现 | `AdminUserController`、`AdminUserImportController`、`users` | 可维护学生、教师、专业范围、密码 |
| 管理员不是专业负责人 | 部分实现 | `/admin/` 与 `/director/` 分开 | 但部分全局开关仍由管理员控制，合理 |
| 专业负责人审题 | 已实现 | `DirectorTopicReviewController`、`TopicDao.review()` | 按 `college/major` 审题 |
| 教师出题 | 已实现 | `TeacherTopicController`、`TopicDao.insert()` | 新题为 `pending` |
| 审核通过后题目不能改 | 未实现 | `TeacherTopicController.edit` 可重新置为 `pending` | 需要锁定 `open/closed` 题目 |
| 学生只能看本专业题目 | 已实现 | `TopicDao.findOpenTopics(keyword,college,major)` | 符合需求 |
| 学生最多 3 个志愿 | 未实现 | 当前单申请模型 | 需要增加志愿明细结构 |
| 至少选择 1 个志愿 | 未实现为三志愿表单 | 当前每次只能申请 1 个 | 单申请天然至少 1，但不符合三志愿 |
| 一个题目最多 3 个学生意向 | 未实现 | 只看 `selected_count/max_students` | 没有限制 pending 意向人数 |
| 第一轮确认由专业负责人做 | 已实现简化版 | `DirectorSelectionConfirmController.confirm` | 但无法看志愿顺序 |
| 尽量满足第一志愿 | 未实现 | 无 `choice_rank` | 页面无法按志愿顺序组织 |
| 第二轮只开放未匹配学生 | 部分实现 | `hasPendingOrApproved()` 阻止已有活跃申请 | 但没有完整轮次状态机 |
| 第二轮只开放未定题目 | 部分实现 | `findOpenTopics()` 查未满额题目 | 若 `max_students>1`，不等于未定题目 |
| 第二轮后强制分配 | 部分实现 | `manualAssign()` | 有界面和 DAO，但仍受一题多人模型影响 |
| 最终一题一人 | 未强制实现 | `topics.max_students` 可大于 1 | 需要唯一约束或最终分配表 |
| 学生上传资料 | 已实现 | `StudentDocumentController`、`DocumentDao.submit()` | 已确认选题后才能上传 |
| 教师给成绩和评语 | 已实现简化版 | `TeacherDocumentController`、`DocumentDao.review()` | 可给文档成绩和反馈 |
| 424 完整成绩模型 | 未实现 | 无评阅教师分配和总评公式 | 可作为增强功能 |

## 11. 最应该优先补的缺口

如果下一步要让系统更符合老师口述需求，优先级建议如下。

### P0：必须补，否则核心选题逻辑不符合需求

1. **改造三志愿数据结构。**
   - 增加申请批次表或在选题表中增加 `choice_rank`。
   - 支持一个学生一轮提交 1 到 3 个题目。

2. **限制每题最多 3 个意向学生。**
   - 统计当前轮次所有有效志愿中该 `topic_id` 的数量。
   - 达到 3 后不允许其他学生再把它作为任何志愿。

3. **强制最终一题一人。**
   - 最好增加最终分配表，并设置 `UNIQUE(student_id)`、`UNIQUE(topic_id)`。
   - 或至少确认时检查该题目是否已有 `approved` 记录。

4. **确认页按题目聚合志愿。**
   - 专业负责人必须看到：题目、候选学生、每个学生第几志愿、是否已被其他题确认。

5. **第二轮只给未匹配学生和未分配题目。**
   - 判断依据应是最终分配结果，而不是 `pending/approved` 混合状态。

### P1：强业务一致性

1. **审核通过后题目锁定。**
   - 教师不能编辑 `open/closed/assigned` 题目。
   - 如需修改，必须由专业负责人退回或开启特殊流程。

2. **明确轮次状态机。**
   - 第一轮选题开放。
   - 第一轮确认开放。
   - 第二轮选题开放。
   - 第二轮确认开放。
   - 强制分配开放。

3. **区分申请状态和最终分配状态。**
   - 申请是志愿意向。
   - 分配是最终结果。
   - 两者不要完全混在一张单申请表里。

### P2：增强功能

1. 评阅教师分配。
2. 导师自评 40%、评阅 20%、答辩 40% 总评。
3. 成绩发布和锁定。
4. 更细的导出表和评定书。

## 12. 结论

当前系统不是一堆空 CRUD，它已经具备比较完整的简化业务链路：

```text
出题、审题、申请、教师建议、专业负责人确认、手动分配、
资料上传、教师审核、答辩安排、成绩查看。
```

但是老师这段口述最强调的是“真实选题业务”，而当前系统在这个最核心部分仍然是“单申请模型”，不是“三志愿两轮匹配模型”。

最需要改的不是页面美化，也不是 AI 助手，而是：

```text
三志愿数据结构
+ 每题最多3人意向
+ 专业负责人按志愿确认
+ 第二轮只处理未匹配对象
+ 最终一题一人数据库约束
+ 审核通过后题目锁定
```

把这几个点补上后，系统的业务逻辑才会真正贴合老师讲的毕业设计管理流程。
