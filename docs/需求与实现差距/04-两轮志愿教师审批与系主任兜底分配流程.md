# 两轮志愿教师审批与系主任兜底分配流程设计

> 目标：把老师强调的真实选题流程单独固化下来，避免后续继续沿用“学生志愿由系主任直接确认”的错误责任链。

---

## 1. 核心结论

当前应采用的业务流程不是：

```text
学生填三志愿 -> 系主任直接确认志愿 -> 生成最终选题
```

而应该是：

```text
教师发布课题
  -> 系主任/专业负责人审核课题
  -> 第一轮学生填报志愿
  -> 对应课题的指导教师审批本课题志愿
  -> 匹配成功则生成最终选题
  -> 第一轮未匹配学生进入第二轮
  -> 第二轮学生再填报志愿
  -> 对应课题的指导教师继续审批
  -> 第二轮仍未匹配学生
  -> 系主任/专业负责人统一兜底分配
```

一句话：

> 第一轮、第二轮的志愿审批权属于“课题指导教师”；两轮结束后仍未匹配的学生，才由系主任/专业负责人统一强制分配。

---

## 2. 角色责任边界

| 角色 | 负责事项 | 不应负责事项 |
|---|---|---|
| 学生 | 浏览已开放课题；每轮提交 1-3 个志愿；查看匹配结果 | 不能绕过教师审批直接获得课题 |
| 指导教师 | 发布课题；审批自己课题收到的志愿；选择是否接收学生；后续审核学生文档 | 不审批其他教师课题；不统一分配其他学生 |
| 系主任/专业负责人 | 审核教师提交的课题是否开放；查看本专业选题进度；两轮后给未匹配学生兜底分配 | 不在第一、第二轮直接替教师审批学生志愿 |
| 管理员 | 控制流程阶段开关；维护用户、字典、公告、系统参数 | 不参与具体课题匹配 |

---

## 3. 标准阶段流转

建议把选题流程拆成 6 个阶段。

| 阶段 | 阶段名 | 开放对象 | 核心动作 |
|---|---|---|---|
| 1 | 教师出题 | 教师 | 教师提交课题 |
| 2 | 课题审核 | 系主任/专业负责人 | 审核课题，通过后课题开放 |
| 3 | 第一轮志愿填报 | 学生 | 未匹配学生提交第一轮 1-3 个志愿 |
| 4 | 第一轮教师审批 | 指导教师 | 教师审批自己课题收到的第一轮志愿 |
| 5 | 第二轮志愿填报与教师审批 | 学生、指导教师 | 未匹配学生再次填报，教师再次审批 |
| 6 | 系主任兜底分配 | 系主任/专业负责人 | 给两轮后仍未匹配学生强制分配剩余课题 |

更细的状态流：

```text
topic_submit
  -> topic_review
  -> round1_select
  -> round1_teacher_review
  -> round2_select
  -> round2_teacher_review
  -> manual_assign
  -> closed
```

如果不想新增太多开关，也可以复用当前：

- `switch.selection`：第一轮学生填报。
- `switch.selection_round2`：第二轮学生填报。
- `switch.manual_assign`：系主任兜底分配。

但需要额外明确：学生填报关闭后，教师仍应能审批本轮已提交的志愿，直到管理员切到下一阶段。

## 4. 数据对象设计

当前已有三张新表可以继续保留：

| 表 | 当前作用 | 是否保留 |
|---|---|---|
| `selection_applications` | 学生某一轮提交的一组志愿 | 保留 |
| `selection_choices` | 每个志愿明细，含志愿顺序 | 保留，但需要补充教师审批语义 |
| `topic_assignments` | 最终一人一题分配结果 | 保留 |

关键调整点：

1. `selection_choices.status` 不再只表示系主任确认结果，而要表示教师审批结果。
2. 教师接收某个志愿后，仍然写入 `topic_assignments`，因为最终结果还是一人一题。
3. 系主任兜底分配仍然写入 `topic_assignments`，但 `source='manual'`。

## 5. 建议状态机

### 5.1 `selection_applications.status`

表示学生本轮这组志愿的整体状态。

| 状态 | 含义 |
|---|---|
| `submitted` | 已提交，等待教师审批 |
| `matched` | 本轮某个志愿已被教师接收，学生已匹配 |
| `unmatched` | 本轮所有志愿均未被接收，学生未匹配 |
| `expired` | 因进入下一轮或流程结束而失效 |
| `cancelled` | 学生撤销或管理员作废，通常可不做 |

如果暂时不改数据库枚举，也可以先把：

- `confirmed` 当作 `matched`
- `expired` 当作 `unmatched/expired`

但长期建议把枚举名改准确，避免以后读代码误解。

### 5.2 `selection_choices.status`

表示单个志愿的审批状态。

| 状态 | 含义 | 操作人 |
|---|---|---|
| `pending` | 学生已提交，等待对应课题教师审批 | 学生提交后生成 |
| `accepted` / `selected` | 教师接收该学生 | 指导教师 |
| `rejected` / `not_selected` | 教师不接收，或学生/题目已被其他匹配占用 | 指导教师/系统 |
| `invalid` | 题目关闭、跨专业、流程切换等导致失效 | 系统 |

当前库里已有 `selected/not_selected/invalid`，为了减少迁移成本，可以暂时这样映射：

| 业务含义 | 现有状态 |
|---|---|
| 教师接收 | `selected` |
| 教师拒绝或自动落选 | `not_selected` |
| 失效 | `invalid` |

### 5.3 `topic_assignments.source`

| 值 | 含义 |
|---|---|
| `round1` | 第一轮教师接收后生成 |
| `round2` | 第二轮教师接收后生成 |
| `manual` | 两轮结束后系主任兜底分配 |

## 6. 第一轮 / 第二轮学生填报规则

### 6.1 学生可填报条件

学生能进入填报页并提交志愿，必须满足：

- 当前处于第一轮或第二轮填报阶段。
- 学生账号状态正常。
- 学生尚未存在 `topic_assignments` 最终分配。
- 学生没有旧流程 `topic_selections.status='approved'` 的最终选题。
- 学生在当前轮次没有有效的 `selection_applications.status='submitted'` 记录。
- 第二轮时，只允许第一轮未匹配的学生填报。

第二轮“未匹配学生”的判断：

```sql
NOT EXISTS (
  SELECT 1 FROM topic_assignments a WHERE a.student_id = 当前学生
)
AND NOT EXISTS (
  SELECT 1 FROM topic_selections s
  WHERE s.student_id = 当前学生 AND s.status='approved'
)
```

可选增强：

```sql
第一轮提交过但没有 matched，也允许第二轮继续填报。
```

### 6.2 可选题目条件

学生可选题目必须满足：

- `topics.status='open'`
- 题目与学生同学院、同专业。
- 题目没有进入 `topic_assignments`。
- 题目没有旧流程 `topic_selections.status='approved'`。
- 当前轮次该题目的意向人数未超过 3。

每题最多 3 人意向，统计对象应该是当前轮次仍有效的志愿：

```sql
SELECT COUNT(*)
FROM selection_choices c
JOIN selection_applications a ON c.application_id=a.id
WHERE c.topic_id=?
  AND c.round=?
  AND c.status='pending'
  AND a.status='submitted';
```

### 6.3 志愿提交规则

- 每轮至少 1 个志愿，最多 3 个志愿。
- 第一志愿必填，第二、第三志愿可选。
- 同一轮同一组志愿不能重复选择同一题目。
- 提交后本轮不能反复修改，除非系统明确支持“撤回重填”。
- 志愿提交后进入对应课题教师的审批列表。

## 7. 教师审批流程

### 7.1 教师可见范围

教师只能看到自己课题收到的志愿：

```sql
selection_choices c
JOIN topics t ON c.topic_id=t.id
WHERE t.teacher_id = 当前教师ID
  AND c.round = 当前轮次
  AND c.status = 'pending'
```

教师页面应按“课题”聚合，而不是简单按学生平铺：

```text
课题 A
  第一志愿  学生甲  [接收] [不接收]
  第二志愿  学生乙  [接收] [不接收]
  第三志愿  学生丙  [接收] [不接收]

课题 B
  第一志愿  学生丁  [接收] [不接收]
```

### 7.2 教师接收某个学生

教师点击“接收”后，系统必须在一个事务内完成：

```text
锁定 choice
锁定 student
锁定 topic
校验 choice 属于当前教师的课题
校验 choice.status='pending'
校验 application.status='submitted'
校验学生尚未有最终分配
校验题目尚未有最终分配
插入 topic_assignments
把当前 choice 置为 selected
把该学生本轮其他 pending 志愿置为 not_selected
把该题目本轮其他 pending 候选置为 not_selected
把该 application 置为 matched/confirmed
把 topics.status 置为 closed，selected_count=1
提交事务
```

这样可以保证：

- 一个学生不会被多个教师同时接收。
- 一个题目不会接收多个学生。
- 接收动作具有原子性。

### 7.3 教师拒绝某个学生

教师点击“不接收”后：

```text
校验 choice 属于当前教师
校验 choice.status='pending'
UPDATE selection_choices SET status='not_selected'
```

然后检查该学生本轮是否还有其他 `pending` 志愿：

- 如果还有：继续等待其他教师审批。
- 如果没有，且没有最终分配：该学生本轮整体 `selection_applications.status='unmatched/expired'`。

如果当前数据库暂时没有 `unmatched` 枚举，可以先置为 `expired`，但页面文案要显示“本轮未匹配”。

### 7.4 教师审批优先级

系统不应该自动要求教师必须按第一志愿优先，但页面应突出显示志愿顺序：

- 第一志愿使用高亮 badge。
- 第二、第三志愿使用普通 badge。
- 同一个题目下默认按 `choice_rank ASC, submit_time ASC` 排序。

是否“必须优先录取第一志愿”属于业务规则，如果老师没有明确说强制，就不要写死。建议实现为：

> 教师可看到志愿顺序，并由教师自主选择接收对象。

## 8. 第一轮结束后的处理

第一轮结束，不等于所有第一轮志愿自动失败。建议分两步：

1. 管理员关闭第一轮填报。
2. 教师完成第一轮审批。

第一轮教师审批截止后：

```text
已进入 topic_assignments 的学生
  -> 不进入第二轮

未进入 topic_assignments 的学生
  -> 可进入第二轮

第一轮仍 pending 的志愿
  -> 系统置为 expired/invalid/not_selected
```

建议提供一个“结束第一轮审批”动作，统一清理第一轮未处理志愿：

```sql
UPDATE selection_choices
SET status='not_selected'
WHERE round=1 AND status='pending';

UPDATE selection_applications
SET status='expired'
WHERE round=1 AND status='submitted'
  AND NOT EXISTS (
    SELECT 1 FROM topic_assignments a
    WHERE a.student_id = selection_applications.student_id
  );
```

---

## 9. 第二轮流程

第二轮和第一轮逻辑基本一致，但学生范围变窄：

- 只面向第一轮未匹配学生。
- 只展示尚未被分配的开放课题。
- 仍然每个学生 1-3 志愿。
- 仍然每题最多 3 人意向。
- 仍然由对应课题教师审批。
- 教师接收后写入 `topic_assignments.source='round2'`。

第二轮结束后：

```text
有 topic_assignments
  -> 匹配完成

无 topic_assignments
  -> 进入系主任兜底分配
```

---

## 10. 系主任兜底分配流程

系主任只在两轮结束后处理仍未匹配的学生。

### 10.1 兜底分配开放条件

必须满足：

- 第一轮填报关闭。
- 第二轮填报关闭。
- 教师审批阶段结束。
- `switch.manual_assign=1`。

### 10.2 系主任可见范围

系主任只能处理本学院、本专业：

```sql
users.college = 当前系主任college
users.major = 当前系主任major
topics.college = 当前系主任college
topics.major = 当前系主任major
```

### 10.3 未匹配学生列表

```sql
SELECT *
FROM users u
WHERE u.role='student'
  AND u.status=1
  AND u.college=?
  AND u.major=?
  AND NOT EXISTS (
    SELECT 1 FROM topic_assignments a WHERE a.student_id=u.id
  )
  AND NOT EXISTS (
    SELECT 1 FROM topic_selections s
    WHERE s.student_id=u.id AND s.status='approved'
  );
```

### 10.4 可分配题目列表

```sql
SELECT *
FROM topics t
WHERE t.status='open'
  AND t.college=?
  AND t.major=?
  AND NOT EXISTS (
    SELECT 1 FROM topic_assignments a WHERE a.topic_id=t.id
  )
  AND NOT EXISTS (
    SELECT 1 FROM topic_selections s
    WHERE s.topic_id=t.id AND s.status='approved'
  );
```

### 10.5 兜底分配事务

```text
锁定学生
锁定题目
校验学生未分配
校验题目未分配
INSERT topic_assignments(source='manual', round=2)
清理该学生所有 pending 志愿
清理该题目所有 pending 志愿
UPDATE topics SET status='closed', selected_count=1
提交事务
```

## 11. 页面与入口设计

### 11.1 学生端

| 页面 | 路径 | 作用 |
|---|---|---|
| 浏览课题/填报志愿 | `/student/topic.action` | 展示可选题目，提交 1-3 志愿 |
| 我的选题 | `/student/my-selection.action` | 展示每轮志愿状态和最终匹配结果 |

学生“我的选题”页面建议展示：

```text
最终匹配：
  如果已有 topic_assignments，显示最终课题、指导教师、来源轮次。

第一轮志愿：
  第一志愿  课题A  待教师审批/已接收/未接收
  第二志愿  课题B  ...

第二轮志愿：
  ...
```

### 11.2 教师端

建议新增或改造：

| 页面 | 路径 | 作用 |
|---|---|---|
| 志愿审批工作台 | `/teacher/choice-review.action` | 教师审批自己课题收到的志愿 |
| 已选学生 | `/teacher/student.action` | 查看最终由自己指导的学生 |

`/teacher/choice-review.action` 建议支持：

- `GET`：按题目聚合展示候选学生。
- `POST action=acceptChoice`：接收某个志愿。
- `POST action=rejectChoice`：拒绝某个志愿。

### 11.3 系主任端

| 页面 | 路径 | 作用 |
|---|---|---|
| 本专业选题进度 | `/director/selection-confirm.action` 或新路径 | 查看两轮匹配结果和未匹配学生 |
| 兜底分配 | `/director/selection-confirm.action?action=assign` | 第二轮后强制分配 |

注意：

> 当前 `/director/selection-confirm.action?action=confirmChoice` 直接确认志愿的能力，应从主流程中移除或降级为特殊管理操作，不应作为第一、第二轮常规审批入口。

## 12. Controller / DAO 改造清单

### 12.1 新增或改造 Bean

可复用：

- `SelectionApplication`
- `SelectionChoice`
- `TopicChoiceGroup`
- `TopicAssignment`

建议新增展示 Bean：

```text
TeacherChoiceGroup
  topicId
  topicTitle
  round
  choices

TeacherChoiceCandidate
  choiceId
  studentId
  studentName
  studentNo
  choiceRank
  submitTime
  status
```

如果现有 `TopicChoiceGroup` 已够用，也可以不新增，直接复用。

### 12.2 DAO 层

建议新增 `TeacherChoiceReviewDao`，避免把教师审批逻辑塞进系主任 DAO。

核心方法：

```java
List<TopicChoiceGroup> findChoiceGroupsByTeacher(int teacherId, int round);

int acceptChoice(int teacherId, int choiceId, String comment);

int rejectChoice(int teacherId, int choiceId, String comment);
```

`acceptChoice` 返回码建议：

| 返回码 | 含义 |
|---|---|
| `>0` | 生成的 `topic_assignments.id` |
| `-1` | 该志愿不属于当前教师 |
| `-2` | 学生已有最终课题 |
| `-3` | 题目已有最终分配 |
| `-4` | 志愿状态不可审批 |
| `-5` | 当前阶段不允许教师审批 |
| `0` | 数据库异常或未知失败 |

### 12.3 Controller 层

新增：



`doPost`：

```text
action=acceptChoice -> dao.acceptChoice
action=rejectChoice -> dao.rejectChoice
redirect 回教师审批页并带 msg
```

### 12.4 JSP 层

新增：

```text

```

页面核心结构：


## 13. 数据一致性规则

必须由数据库约束和事务共同保证。

### 13.1 一个学生最终只能一个题目

已由 `topic_assignments` 保证：

```sql
UNIQUE KEY uk_topic_assignment_student (student_id)
```

### 13.2 一个题目最终只能一个学生

已由 `topic_assignments` 保证：

```sql
UNIQUE KEY uk_topic_assignment_topic (topic_id)
```

### 13.3 一个学生同轮只能提交一组有效志愿

建议继续使用：

```sql
UNIQUE KEY uk_selection_app_student_round_active (student_id, round, active_guard)
```

### 13.4 同一组志愿不能重复题目

已有：

```sql
UNIQUE KEY uk_selection_choice_application_topic (application_id, topic_id)
```

### 13.5 每题每轮最多 3 个意向

这个规则不容易用普通唯一键直接表达，必须在 `submitChoices` 事务里：

```text
SELECT topic FOR UPDATE
统计当前轮次 pending 意向人数
如果 >=3，则拒绝提交
```

## 14. 与当前实现的差距

当前已经具备：

- 学生提交 1-3 个志愿。
- 每轮一组有效志愿。
- 每题意向人数限制。
- 最终分配表 `topic_assignments`。
- 系主任兜底分配的基础能力。

本轮改造后已经补齐：

| 需求 | 当前实现 | 状态 |
|---|---|---|
| 第一、二轮由对应教师审批 | 新增 `/teacher/choice-review.action` | 已实现 |
| 教师查看自己题目的志愿候选 | `TeacherChoiceReviewDao.findChoiceGroupsByTeacher` 只查当前教师课题 | 已实现 |
| 教师接收志愿后生成最终分配 | `TeacherChoiceReviewDao.acceptChoice` 写入 `topic_assignments` | 已实现 |
| 教师拒绝某个志愿 | `TeacherChoiceReviewDao.rejectChoice` 将该志愿置为 `not_selected` | 已实现 |
| 系主任不再作为一二轮常规审批人 | `/director/selection-confirm.action?action=confirmChoice` 已改为提示走教师审批 | 已实现 |

## 17. 答辩表述建议

可以这样讲：

```text
系统选题采用两轮志愿匹配机制。学生每轮最多填报三个志愿，
每个课题每轮最多接收三个学生意向。志愿提交后并不是由系主任直接确认，
而是进入对应课题指导教师的审批工作台。指导教师只能审批自己课题下的候选学生，
接收后系统在事务中生成最终选题分配，保证一个学生只能匹配一个课题、
一个课题也只能分配给一个学生。第一轮未匹配的学生进入第二轮继续填报，
第二轮结束后仍未匹配的学生，才由系主任在本专业范围内进行兜底分配。
```

如果当前代码还没完全改完，答辩前不要说“已经完全按教师审批实现”，而应说：

```text
当前已完成三志愿填报、最终分配和系主任兜底分配基础能力；
下一步将第一、第二轮志愿确认入口从系主任端调整到对应指导教师端，
```

## 18. 最终验收标准

这个模块只有同时满足下面条件，才能算完全符合老师需求：

- 学生可以按轮次提交 1-3 个志愿。
- 每题每轮最多 3 个学生表达意向。
- 第一轮志愿由对应课题指导教师审批。
- 第二轮志愿仍由对应课题指导教师审批。
- 教师只能审批自己的课题。
- 教师接收后生成最终一人一题分配。
- 一个学生最终只能有一个题目。
- 一个题目最终只能给一个学生。
- 第一轮未匹配学生才能进入第二轮。
- 第二轮未匹配学生才进入系主任兜底分配。
- 系主任兜底分配只能处理本专业未匹配学生和未分配题目。
- 学生端、教师端、系主任端都能看到一致的最终结果。
