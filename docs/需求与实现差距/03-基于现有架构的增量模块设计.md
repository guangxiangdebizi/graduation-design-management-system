# 基于现有架构的核心选题模块增量设计

> 目标：不推翻当前 JSP + Servlet Controller + DAO + MySQL 架构，在现有代码结构上补齐老师强调的核心业务：三志愿、每题最多 3 人意向、两轮选题、专业负责人确认、强制一题一人、题目审核后锁定。

---

## 1. 设计原则

当前项目已经形成固定分层：

```text
JSP 页面
  -> Controller(Servlet)
  -> DAO
  -> SQLHelper / JDBC
  -> MySQL
```

所以新增模块不单独引入 Spring、不重写前后端、不做大规模技术栈迁移，而是沿用当前风格：

- 新增 JavaBean 放在 `src/bean/`。
- 新增 DAO 放在 `src/dao/`。
- 新增 Controller 放在 `src/controller/`。
- 新增 JSP 放在 `WebContent/student/`、`WebContent/director/`。
- 新增数据库结构放在 `sql/migrate_selection_choice_flow_YYYYMMDD.sql`。
- 旧的 `topic_selections` 尽量保留兼容，新的三志愿和最终分配用新表承接。

---

## 2. 模块拆分

建议增加 5 个核心子模块：

| 模块 | 作用 | 主要用户 |
|---|---|---|
| 选题批次模块 | 记录某学生第几轮提交了一组选题志愿 | 学生、专业负责人 |
| 志愿明细模块 | 记录第一/第二/第三志愿及题目意向人数 | 学生、专业负责人 |
| 最终分配模块 | 独立记录最终一人一题、一题一人结果 | 专业负责人、学生、教师 |
| 轮次状态模块 | 控制第一轮、第二轮、确认、强制分配阶段 | 管理员/可由管理员开关控制 |
| 确认工作台模块 | 按题目聚合显示候选学生和志愿顺序 | 专业负责人 |

## 3. 数据库增量设计

### 3.1 新增选题申请批次表 `selection_applications`

表示某学生在某一轮提交了一组志愿。

```sql
CREATE TABLE selection_applications (
    id INT AUTO_INCREMENT PRIMARY KEY,
    student_id INT NOT NULL,
    round TINYINT NOT NULL,
    status ENUM('submitted','confirmed','expired','cancelled') NOT NULL DEFAULT 'submitted',
    submit_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (student_id) REFERENCES users(id),
    UNIQUE KEY uk_student_round_active (student_id, round, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

说明：

- `round` 只允许 1 或 2。
- `status='submitted'` 表示本轮志愿仍可被专业负责人确认。
- 一个学生同一轮只能有一组有效志愿。

> 如果 MySQL 不适合对 `ENUM` 状态做复杂唯一约束，可以改为增加 `active_guard` 生成列，沿用当前 `topic_selections.active_guard` 的做法。

### 3.2 新增志愿明细表 `selection_choices`

表示某申请批次下的第 1/2/3 志愿。

```sql
CREATE TABLE selection_choices (
    id INT AUTO_INCREMENT PRIMARY KEY,
    application_id INT NOT NULL,
    student_id INT NOT NULL,
    topic_id INT NOT NULL,
    round TINYINT NOT NULL,
    choice_rank TINYINT NOT NULL,
    status ENUM('pending','selected','not_selected','invalid') NOT NULL DEFAULT 'pending',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (application_id) REFERENCES selection_applications(id),
    FOREIGN KEY (student_id) REFERENCES users(id),
    FOREIGN KEY (topic_id) REFERENCES topics(id),
    UNIQUE KEY uk_application_rank (application_id, choice_rank),
    UNIQUE KEY uk_application_topic (application_id, topic_id),
    CHECK (choice_rank BETWEEN 1 AND 3),
    CHECK (round IN (1, 2))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

说明：

- 一个申请批次最多 3 行。
- `choice_rank=1` 表示第一志愿。
- 同一批次不能重复选择同一个题目。
- `status='selected'` 表示这个志愿最终被确认。
- `status='not_selected'` 表示同批次其他志愿或同题目其他候选落选。

### 3.3 新增最终分配表 `topic_assignments`

这是系统最终结果，必须独立于志愿申请。

```sql
CREATE TABLE topic_assignments (
    id INT AUTO_INCREMENT PRIMARY KEY,
    student_id INT NOT NULL,
    topic_id INT NOT NULL,
    choice_id INT DEFAULT NULL,
    round TINYINT NOT NULL DEFAULT 1,
    source ENUM('round1','round2','manual') NOT NULL,
    confirmed_by INT NOT NULL,
    confirm_comment TEXT,
    confirm_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (student_id) REFERENCES users(id),
    FOREIGN KEY (topic_id) REFERENCES topics(id),
    FOREIGN KEY (choice_id) REFERENCES selection_choices(id),
    FOREIGN KEY (confirmed_by) REFERENCES users(id),
    UNIQUE KEY uk_assignment_student (student_id),
    UNIQUE KEY uk_assignment_topic (topic_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

关键点：

- `UNIQUE(student_id)` 保证一个学生最终只有一个题目。
- `UNIQUE(topic_id)` 保证一个题目最终只给一个学生。
- 这是“一人一题、一题一人”的数据库兜底。

### 3.4 系统配置新增阶段状态

继续沿用 `system_configs`：

```sql
INSERT INTO system_configs(config_key, config_value, description) VALUES
('selection.phase', 'round1_select', '当前选题阶段'),
('selection.intent_limit', '3', '每个题目每轮最多志愿意向人数'),
('selection.choice_limit', '3', '每个学生每轮最多志愿数')

```

`selection.phase` 建议取值：

| 值 | 说明 |
|---|---|
| `topic_submit` | 教师出题 |
| `topic_review` | 专业负责人审题 |
| `round1_select` | 第一轮学生选题 |
| `round1_confirm` | 第一轮专业负责人确认 |
| `round2_select` | 第二轮学生选题 |
| `round2_confirm` | 第二轮专业负责人确认 |
| `manual_assign` | 强制分配 |

## 5. DAO 设计

### 5.1 `SelectionChoiceDao`

路径：`src/dao/SelectionChoiceDao.java`

核心方法：

```java
public List<Topic> findSelectableTopics(int studentId, int round);

public int submitChoices(int studentId, int round, List<Integer> topicIds);

public SelectionApplication findActiveApplication(int studentId, int round);

public List<SelectionChoice> findChoicesByStudent(int studentId);

public List<TopicCandidateGroup> findCandidateGroups(String college, String major, int round);

public int countTopicIntent(Connection conn, int topicId, int round);
```

`submitChoices` 必须使用事务：

```text
BEGIN
  锁定学生行
  检查学生属于 student 且启用
  检查学生还没有最终分配
  检查当前阶段允许该 round 选题
  检查 topicIds 数量 1-3 且不重复
  对每个 topic FOR UPDATE
    检查题目 open、同专业、未最终分配
    检查本轮意向人数 < 3
  插入 selection_applications
  插入 selection_choices
COMMIT
```

返回码建议：

| 返回码 | 含义 |
|---:|---|
| `>0` | applicationId |
| `-1` | 已有最终分配 |
| `-2` | 当前阶段不允许选题 |
| `-3` | 志愿数量非法 |
| `-4` | 志愿重复 |
| `-5` | 题目不在本专业或不可选 |
| `-6` | 题目意向人数已满 |
| `0` | 其他失败 |

### 5.2 `TopicAssignmentDao`

路径：`src/dao/TopicAssignmentDao.java`

核心方法：

```java
public TopicAssignment findByStudent(int studentId);

public TopicAssignment findByTopic(int topicId);

public List<User> findUnassignedStudents(String college, String major);

public List<Topic> findUnassignedTopics(String college, String major);

public int confirmChoice(int choiceId, String college, String major, int directorId, String comment);

public int manualAssign(int studentId, int topicId, String college, String major, int directorId, String comment);
```

`confirmChoice` 事务规则：

```text
BEGIN
  锁定 choice/application/student/topic
  检查 choice 属于 director 的 college+major
  检查学生无最终分配
  检查题目无最终分配
  INSERT topic_assignments
  UPDATE selection_choices SET status='selected' WHERE id=?
  UPDATE 同学生其他 choice SET status='not_selected'
  UPDATE 同题目其他 choice SET status='not_selected'
  UPDATE selection_applications SET status='confirmed'
  UPDATE topics SET selected_count=1,status='closed'
COMMIT
```

返回码建议：

| 返回码 | 含义 |
|---:|---|
| `1` | 成功 |
| `-1` | 学生已有最终分配 |
| `-2` | 题目已有最终分配 |
| `-3` | 越权或专业不匹配 |
| `-4` | 当前阶段不允许确认 |
| `0` | 其他失败 |

### 5.3 旧 `SelectionDao` 的定位

当前 `SelectionDao` 负责旧的单申请模型。新增模块后有两种处理方式：

#### 方案 A：保留旧表兼容，新增三志愿模块为主

- 旧的 `/student/topic.action?action=apply` 后续不再作为主入口。
- 新入口仍使用 `/student/topic.action`，但提交动作改为 `action=submitChoices`。
- 旧 `topic_selections` 可继续服务文档上传等老逻辑，但最终建议让文档上传改查 `topic_assignments`。

#### 方案 B：直接改造旧 `topic_selections`

- 增加 `choice_rank`。
- 允许同一学生同一轮最多 3 条 pending。
- 但会破坏当前 `active_guard` 唯一约束。

建议采用 **方案 A**，风险小、回滚容易、和当前代码冲突少。

### 8.3 文档上传查询最终选题

当前 `StudentDocumentController` 依赖：

```java

```

新增最终分配表后，应改为优先查：

```java
TopicAssignment assignment = new TopicAssignmentDao().findByStudent(user.getId());
```

兼容策略：

```text
先查 topic_assignments
如果没有，再查旧 topic_selections approved
```

这样不会破坏已有演示数据。

### 8.4 教师学生列表和文档审核

当前很多查询通过：

```text
topic_selections.status='approved'
```

新增后应逐步改为：

```text
topic_assignments JOIN topics ON assignment.topic_id=topics.id
```

兼容期可以用 UNION：

```sql
-- 新最终分配
SELECT ... FROM topic_assignments a JOIN topics t ...
UNION
-- 旧 approved 选题
SELECT ... FROM topic_selections s JOIN topics t ... WHERE s.status='approved'
```

## 9. 题目锁定设计

当前问题：教师可以编辑已审核通过的题目。

最小改法：

### 9.1 `TopicDao.update` 增加状态限制

教师只能修改：

```text
pending
rejected
```

不能修改：

```text
open
closed
```

SQL 改为：

```sql
UPDATE topics
SET title=?, description=?, college=?, major=?, max_students=?, status='pending',
    review_comment=NULL, reviewer_id=NULL, review_time=NULL
WHERE id=? AND teacher_id=? AND status IN ('pending','rejected')
```

### 9.2 JSP 按状态禁用编辑按钮

`WebContent/teacher/topics.jsp`：

```text
pending/rejected：显示“编辑并重提”
open/closed：显示“已审核锁定”
```

## 10. 一题一人设计

最终分配表已经用：

```sql
UNIQUE KEY uk_assignment_student (student_id)
UNIQUE KEY uk_assignment_topic (topic_id)
```

保证一题一人。

同时建议将新流程中题目 `max_students` 弱化：

- 老字段保留，避免影响旧页面。
- 新志愿确认不再以 `max_students` 判断最终容量。
- 题目一旦进入 `topic_assignments`，就视为不可再选。
- 题目确认后同步 `topics.selected_count=1,status='closed'`。

## 13. 答辩讲法

如果答辩时解释新增设计，可以这样说：

```text
原系统已经具备教师出题、专业负责人审题、学生申请、确认和文档上传的基础流程。
但老师强调选题不是选课，所以我把选题拆成“志愿申请”和“最终分配”两层：

第一层 selection_applications + selection_choices 记录学生每轮最多 3 个志愿；
第二层 topic_assignments 记录专业负责人确认后的最终结果。

这样既能支持第一/第二/第三志愿，也能用唯一约束保证最终一题一人、一人一题。
第二轮时，系统只查询没有 topic_assignments 的学生和题目，避免所有学生重新乱选。
```
